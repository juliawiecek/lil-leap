# TS-01.5 registration contract and rollout

Registration uses the existing normalized entities. Orders and Holdings now match
the current `finalized-schema.sql`, including encrypted SSN in `customer_profiles`
(the current schema has no `users.ssn` column), JSONB disclosures, and database
net-worth tokens. Insights already had those mappings. All three Java services
save the user, customer profile, financial profile, and existing trading account
inside one Spring transaction. The extracted NestJS service retains its transaction.

## Request compatibility (TS-01.3)

The checked-in forms in `frontend/src/app/investor-profile.ts` and
`insights-frontend/src/app/investor-profile.ts` already use `date_of_birth` and
`citizenship_status`; field names and the Java camelCase response stay unchanged.
Both forms allow applicants from their 21st birthday and submit to
`POST /api/v1/users`. Form string values are converted to JSON booleans where
required; empty optional KYC fields and inactive conditional fields are omitted.
SSN is required to match the finalized schema. Only a successful HTTP 201 response
with a user ID completes registration. Duplicate email, validation, and network
errors keep the user on the review screen; submission is disabled while pending.

After registration the UI clears credentials and returns to sign-in. Sign-in
calls `POST /api/v1/auth/login` and opens the dashboard only after receiving a
token. The token stays in memory and is cleared on sign-out; passwords, SSN, and
tokens are not written to browser storage. The Orders frontend proxies the login
URL to its backend's `/auth/login`; Insights uses its existing `/api/v1` context.
Angular development proxies and the Orders nginx route support the same browser
URLs. Frontend/backend compatibility is verified directly by the browser tests
below; no API field rename or separate frontend change is pending.

Orders and Holdings keep `POST /api/v1/users` and also accept
`POST /clients/register`. Insights keeps `POST /users` and adds
`POST /clients/register`, both relative to its configured `/api/v1` context path.
Both Java routes allow anonymous POST requests. The extracted Identity Service
keeps `POST /auth/register` and its role-specific behavior.

Example Java request, with no full KYC collection:

```json
{
  "first_name": "Test",
  "last_name": "Client",
  "date_of_birth": "2000-01-01",
  "email": "client@example.test",
  "password": "Password123!",
  "phone": "555-0100",
  "street_address": "1 Test Way",
  "city": "Test City",
  "state_province": "TX",
  "postal_code": "12345",
  "country": "US",
  "citizenship_status": "CITIZEN",
  "ssn": "111-22-3333",
  "account_name": "Trading",
  "account_type": "INDIVIDUAL_CASH",
  "trader_level": "NOVICE"
}
```

`date_of_birth` is required in `YYYY-MM-DD` format. Missing, future, or under-21
birth dates return HTTP 400. `citizenship_status` is required and accepts `CITIZEN`,
`PERMANENT_RESIDENT`, or `OTHER`. Phone and SSN are required by the current schema;
phone length is limited to 20 characters and email to 255.

Employment, income, net worth, risk, accreditation, and regulatory disclosure
fields are optional. Existing complete onboarding requests remain supported,
including conditional detail validation when a disclosure is affirmative.
Omitted accreditation defaults to false; KYC starts at `PENDING` and source-of-funds
verification starts at false. Explicit self-reported accreditation is preserved.
Existing account fields remain required to preserve account creation and response
semantics. Credentials and SSN are never included in the registration response.

## Database rollout

Fresh installations load `db/finalized-schema.sql`. On an existing normalized
database, apply `db/migrations/008_registration_minimum_age.sql` as the schema
owner before deploying the application changes. The current requirement is 21+,
superseding the original ticket's 18+ acceptance criterion. This migration replaces
any earlier age constraint and trigger with the 21+ rule. If the earlier 18+ version
of migration 008 was applied locally, rerun this revised version. It stops and rolls
back if existing customers are under 21; it never deletes customers or changes DOBs.
Those records need an explicit data-policy decision before migration can proceed.
Do not reset persistent volumes. An installation still using the historical
embedded-address schema needs a separate backfill: DOB and citizenship cannot be
inferred from its old records.

Configure the same SSN encryption key in all services using
`NEXTTRADE_SECURITY_SSN_ENCRYPTION_KEY` (Spring property
`nexttrade.security.ssn-encryption-key`). Compose passes the root environment's
required `SSN_ENCRYPTION_KEY` to all four services. PostgreSQL must have `pgcrypto`, as
installed by the finalized schema. Use UTC for the database session date to match
the Java age cutoff.

## Verification

Each Java service includes `RegistrationPersistenceTest`. It uses the real
finalized PostgreSQL schema, a real password encoder, pgcrypto, and real Spring
transactions. It covers both routes, exact 21st birthday, underage/future DOB,
missing identity fields, duplicate email, linked records/defaults, full KYC
mapping, and rollback when customer, financial, or account persistence fails.
Each run creates and drops its own randomly named schema.

Set `REGISTRATION_TEST_DB_URL` to a disposable PostgreSQL JDBC URL, plus
`REGISTRATION_TEST_DB_USER` and `REGISTRATION_TEST_DB_PASSWORD`, then run `mvn test`
from each Java service. The database user must be able to create schemas and
install pgcrypto. These integration tests are skipped when the URL is absent.
Java 25 users running the current Mockito version also need
`-Dnet.bytebuddy.experimental=true`; the project targets Java 21 or earlier.

Run `npm test -- --runInBand` and `npm run build` in `auth` for the extracted
service. Database boundary checks are in `db/tests/002_behavior_tests.sql`.

Run `npm test` from `frontend` for API-contract and error-handling tests covering
both frontends. Run `npm run build` in each frontend for production compilation.

For browser verification, use a disposable database initialized with the finalized
schema, start Orders on port 8082 and Insights on port 8081 with the same SSN key,
then run `npm start -- --port 4200` in `frontend` and
`npm start -- --port 4201` in `insights-frontend`. From `frontend`:

```powershell
npx playwright install chromium
npm run test:e2e -- --output=test-results/orders
$env:FRONTEND_E2E_URL = 'http://127.0.0.1:4201'
npm run test:e2e -- --output=test-results/insights
Remove-Item Env:FRONTEND_E2E_URL
```

The browser suite registers an applicant on their exact 21st birthday without
full KYC, reloads the page, rejects a wrong password, signs in using persisted
credentials, verifies the issued token against `/users/me`, and signs out. It also
checks underage UI rejection, duplicate-email handling, and network failure/retry.
Tests create synthetic `ts015-...@example.test` accounts in the disposable database;
they do not run against production. Request traces and videos are disabled.
