# TS-06.3: Location/jurisdiction restrictions

New order submissions enforce instrument restrictions against the authenticated
client's **registered country**, read from `customer_profiles.country`. Country is
the structured location field available in the current registration schema.
State/province, IP geolocation, citizenship, and request-supplied location are not
used by this check. This story implements country-level jurisdiction rules.

## Behavior and acceptance criteria

| Criterion | Implementation |
| --- | --- |
| AC1: Client location restrictions are enforced | Resolve registered country and look up an enabled rule for the resolved instrument ID and country code. |
| AC2: Restricted trades are rejected | Reject both BUY and SELL with HTTP 422 before saving an order. Cash, holdings, and fills remain unchanged. |
| AC3: Automated tests verify restrictions | Country normalization, actual JDBC rule queries, submission ordering, API responses, PostgreSQL requests, and SQL permission tests cover the rule. |

The flow is: authenticate -> authorize account ownership -> return an existing
idempotent order if present -> resolve tradable instrument -> check jurisdiction ->
check cash/holdings -> save `SUBMITTED` order.

`RegisteredCountry` accepts ISO alpha-2/alpha-3 codes and English country names
provided by the Java runtime, ignoring case and surrounding/repeated whitespace.
Examples: `US`, `USA`, `United States`, and `United States of America` all match `US`;
`UK`, `GBR`, and `United Kingdom` match `GB`. Unknown values are rejected rather than
guessed. Restriction rules must use the resolved uppercase ISO alpha-2 code.

| Condition | Response |
| --- | --- |
| Enabled restriction matches instrument and country | 422 `LOCATION_RESTRICTED` |
| Missing profile, null/blank country, or unrecognized country | 422 `LOCATION_UNAVAILABLE` |
| Recognized country with no matching enabled restriction | Continue to other checks; 201 `SUBMITTED` if they pass |
| Retry of an existing account/clientReference | 200 with the original order; no new trade or validation |

The response contains a fixed `error` code and `message`. It never includes the
client's country or an operator's internal rule reason. Different instruments and
different registered countries are evaluated independently. Rules are queried on
every new submission, so committed rule changes apply without an application restart.

There is **no built-in real-world restriction list**: the story supplies none.
Operators must populate approved policy. An empty rule table permits recognized
countries through this particular check. The examples/tests use synthetic policy
and must not be interpreted as actual trading or legal restrictions.

As with TS-06.1, this is a submission check. A future acceptance/execution workflow
must recheck current jurisdiction policy before accepting/executing a pending order.
Returning an existing submission is not a new acceptance or execution.

## Database setup

Fresh databases use the updated `db/finalized-schema.sql` and `db/init-app-role.sh`.
For an existing database, apply the additive migration **before running this code**.
From the repository root, replace the database/owner names and runtime role as needed:

```powershell
psql -h localhost -U YOUR_DB_OWNER -d YOUR_DATABASE -v app_user=app_user -f db/migrations/007_instrument_jurisdiction_restrictions.sql
```

This creates the table without dropping data and grants the runtime role `SELECT`
only. It can be reapplied and preserves existing rules. There is no automatic
migration runner in this repository; restarting Compose with an existing database
volume does not apply this SQL. Do not reset the volume to apply this change.

## Maintaining rules

An authorized operator uses the schema-owner/maintenance database connection. The
application's trading credentials cannot insert, update, delete, or truncate rules;
there is no client-facing rule-management endpoint.

In `psql`, set `instrument_id`, `country_code`, and `reason` to an approved policy.
Resolve the instrument by **market and symbol**, since symbols can exist on more
than one market. These variables are deliberately not filled with a real policy:

```sql
INSERT INTO instrument_jurisdiction_restrictions
    (instrument_id, country_code, enabled, reason)
VALUES (:'instrument_id'::uuid, :'country_code', TRUE, :'reason')
ON CONFLICT (instrument_id, country_code)
DO UPDATE SET enabled = TRUE, reason = EXCLUDED.reason, updated_at = CURRENT_TIMESTAMP;

-- Disable an existing restriction:
UPDATE instrument_jurisdiction_restrictions
SET enabled = FALSE, updated_at = CURRENT_TIMESTAMP
WHERE instrument_id = :'instrument_id'::uuid AND country_code = :'country_code';
```

Each instrument/country pair is unique. The schema rejects malformed country keys,
blank reasons, and nonexistent instruments. Use recognized ISO codes (`GB`, not
`UK`, for example); the database checks key format, while the service normalizes
registered country values.

## Verification

Run from the repository root with Java 21 and Maven:

```powershell
mvn -B -f insights/pom.xml '-Dtest=OrderJurisdictionServiceTest,JdbcOrderJurisdictionRepositoryTest,OrderSubmissionServiceTest,OrderSubmissionControllerTest' test
mvn -B -f insights/pom.xml verify
```

The standard suite requires no external database and includes real JDBC queries
against H2. `PostgresContractTest` additionally uses the real schema, security chain,
submission service, and repositories. Configure a **disposable test database** and a
test fixture role allowed to maintain restriction rules (for example its schema
owner). This fixture permission must not be added to the runtime application role:

```powershell
$env:TEST_POSTGRES_URL = 'jdbc:postgresql://localhost:5432/nexttrade_test'
$env:TEST_POSTGRES_USER = 'YOUR_TEST_FIXTURE_ROLE'
# Set TEST_POSTGRES_PASSWORD to that test role's password.
mvn -B -f insights/pom.xml verify
```

PostgreSQL tests cover restricted BUY/SELL requests even with spoofed location
headers/body, missing locations, enabling/disabling rules, registration persistence,
unchanged financial data, and idempotent retries after a rule changes. They are
skipped if `TEST_POSTGRES_URL` is absent. Most fixtures roll back; the concurrency
fixture is committed and cleaned up after the test.

Verify actual runtime permissions and database constraints as the test schema owner:

```powershell
psql -h localhost -U YOUR_TEST_DB_OWNER -d nexttrade_test -v app_user=app_user -f db/tests/007_jurisdiction_restrictions.sql
```

For manual API checks, use an owned, funded test account with a recognized registration
country and a quoted instrument. Enable a synthetic restriction for that pair: BUY
and SELL must return `LOCATION_RESTRICTED`. Disable it and use a **new clientReference**:
the order should proceed through sufficiency validation. Check that rejected requests
created no orders/fills or cash/holdings changes.
